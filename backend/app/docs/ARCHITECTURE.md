Three subtrees are present but currently empty (just an `__init__.py`): `modules/auth/`,
`modules/progress/`, and `opening_importer/` (with its `importer/`/`seed/` children). They
read as placeholders for future work rather than active code — don't assume functionality
lives there. Per `AGENTS.md`, `modules/progress/` is intentionally reserved for a future
progress-tracking feature, and `modules/openings/service.py::get_prompt_and_move()` is the
documented target interface for an upcoming "real opening-dataset-driven selection" feature
— neither is accidental dead code, even though nothing calls them yet.

## High-Level Request Flow

1. Request arrives at a FastAPI router in `backend/app/routers/` (`auth.py`, `openings.py`, `training.py`).
2. Training/openings routers call into module services (`backend/app/modules/training/service.py`,
   `backend/app/modules/openings/service.py`). Auth has no separate service module — `routers/auth.py`
   itself contains password hashing (`hash_password`/`verify_password`) and JWT issuance/verification
   (`create_access_token`, `create_refresh_token`, `get_current_user`).
3. Services operate on domain models in `backend/app/modules/*/models.py`, using move-legality
   rules from `backend/app/modules/training/chess_rules.py`.
4. Persistence goes through the engine/session/`Base`/`get_db` defined in
   `backend/app/modules/shared/db.py`, with schema managed by Alembic migrations in
   `backend/app/migrations/`.
5. Training and item endpoints enforce per-user ownership: `TrainingSession.user_id` is checked
   against the authenticated user (from `Depends(get_current_user)`) before any session/item is
   read or written; a mismatch returns 404 rather than another user's data.

## Component Overview

### Routers (`backend/app/routers/`)
- `auth.py` — register/login/refresh/me, plus password hashing and JWT helpers
- `openings.py` — `GET /openings` (public, no auth)
- `training.py` — training-session CRUD + move submission (all endpoints require auth)

### Services (`backend/app/modules/*/service.py`)
- `modules/training/service.py` — session creation, next-item lookup, response submission, bulk item creation
- `modules/openings/service.py` — `get_prompt_and_move()`; not currently called from any router, but documented in `AGENTS.md` as the intended interface for a planned dataset-driven item-selection feature

### Domain Models
- `modules/users/models.py` — `User`
- `modules/openings/models.py` — `Opening` (composite PK: `eco` + `name`)
- `modules/training/models.py` — `TrainingSession`, `TrainingItem`, `TrainingResponse`

`TrainingSession.opening_eco`/`opening_name` are plain `String` columns with no ORM
`ForeignKey`/`relationship` to `Opening` — but a composite FK (`ondelete="RESTRICT"`) *is*
enforced at the DB level (migration `7f740a9c4e3a`). So `session.opening` isn't navigable
in Python, even though the database won't let an opening be deleted while a session
references it.

### Rules / Validation Helpers
- `modules/training/chess_rules.py` — `validate_and_apply()`: parses a UCI move, checks legality, and compares against the expected correct move

### DB Plumbing / Migrations
- `modules/shared/db.py` — engine, `SessionLocal`, `Base`, `get_db` (the only DB wiring in the app)
- `app/migrations/` (Alembic) — `env.py` walks every `modules/*/models.py` to build `target_metadata`

### Opening Data Import
- `scripts/import_openings.py` (repo root) — downloads lichess ECO TSVs, computes EPD/UCI move lists via `python-chess`, and upserts into the `openings` table with raw `psycopg`. This is the real importer; `backend/app/opening_importer/` is an empty placeholder, not where this logic lives.

## Key Architecture Decisions

| Decision | Implementation |
|---|---|
| API design | FastAPI routers grouped by feature area (`routers/auth.py`, `routers/openings.py`, `routers/training.py`) |
| API casing | Response/request models extend `CamelModel` (`routers/training.py`) so JSON is camelCase while Python stays snake_case |
| Business logic placement | Training/openings workflows live in `modules/*/service.py`; auth logic lives directly in `routers/auth.py` (no separate auth service module exists) |
| Domain boundaries | Feature-specific model files (`modules/*/models.py`) |
| Rules location | Move legality/correctness kept in `modules/training/chess_rules.py` |
| Persistence and migrations | Central DB plumbing in `modules/shared/db.py`, Alembic migrations in `app/migrations/` |
| Authorization | JWT bearer tokens (`routers/auth.py`); training/item lookups are scoped to `current_user.id` via `TrainingSession.user_id` |
| Opening data import | Offline script (`scripts/import_openings.py`) using raw `psycopg`, run manually via `docker compose exec api python scripts/import_openings.py` — not part of the request path |

## Frontends & Shared Chess Core

The backend is UI-agnostic: two interchangeable SPAs — `react/` (Vite, served at `/`) and
`angular/` (Angular 19, served at `/angular/`) — call the same root-absolute `/api`, so
everything is same-origin (no CORS). nginx is the only integration point.

Chess logic that is **not** UI-specific (FEN handling, move validation, opening-preview
positions — all `chess.js`, no framework code) lives in a standalone package,
`packages/chess-core` (`@knight-school/chess-core`):

- **Shared, not copied.** Each frontend depends on it via a **`file:` dependency**
  (`file:../packages/chess-core`), giving one source of truth.
- **Isolated `node_modules`.** No npm workspaces / hoisting — React and Angular keep entirely
  separate dependency trees; only the built package is shared.
- **Built + tested independently.** `tsup` emits an ESM bundle + `.d.ts`; the package's own
  vitest suite exercises the real `chess.js`. The UIs mock the package boundary and test only
  their own wiring. Its CI job is `.github/workflows/core.yml`.
- **Docker.** `react/Dockerfile` builds the package (its own isolated install + build) before
  installing React, which resolves the `file:` dep against it.
