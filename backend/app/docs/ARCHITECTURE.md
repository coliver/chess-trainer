Two subtrees contain only an `__init__.py`: `modules/auth/` and `opening_importer/` (with its
`importer/`/`seed/` children). Don't assume functionality lives there. Auth logic is in
`routers/auth.py`, and the real importers are in the root `scripts/`.

`modules/openings/service.py::get_prompt_and_move()` is not imported by any router or other
module; only `tests/test_openings_service.py` exercises it.

## High-Level Request Flow

1. A request arrives at a FastAPI router in `backend/app/routers/`.
2. Routers hold request/response models and thin routing, and delegate to module services
   (`modules/training/service.py`, `modules/progress/service.py`,
   `modules/puzzles/service.py`). `openings.py` queries the `Opening` model directly, and
   `users.py` validates and writes preferences directly on the `User` row. Auth has no service
   module: `routers/auth.py` contains password hashing (`hash_password`/`verify_password`, PBKDF2-SHA256),
   token issuance (`create_access_token`, `create_refresh_token`, `create_email_verification_token`)
   and the `get_current_user` / `get_current_user_or_none` dependencies.
3. Services operate on models in `backend/app/modules/*/models.py`. Move legality comes from
   `modules/training/chess_rules.py` (used by both training and puzzles); scheduling comes
   from the pure `progress/srs.py` and `progress/streak.py`.
4. Persistence goes through `modules/shared/db.py` (`DATABASE_URL` is required at import time),
   with schema managed by Alembic migrations in `backend/app/migrations/`.
5. Authenticated endpoints depend on `get_current_user` (Bearer access token) and scope data to
   `current_user.id`. Training endpoints check `TrainingSession.user_id` against the caller and
   return 404 on mismatch. Progress and puzzle-progress queries filter by `user_id`.

## Component Overview

### Routers (`backend/app/routers/`)

| Router | Endpoints | Auth |
|---|---|---|
| `auth.py` (`/auth`) | `POST /register`, `POST /login`, `POST /refresh`, `GET /me`, `GET /verify-email`, `POST /resend-verification` | public except `/me` |
| `openings.py` | `GET /openings` | public |
| `training.py` | `POST /training-sessions`, `POST /training-sessions/from-due`, `GET /training-sessions/{id}/next`, `POST /training-sessions/{id}/responses`, `POST /training-sessions/{id}/items` | required |
| `progress.py` | `GET /progress/summary`, `/progress/due`, `/progress/step-accuracy`, `/progress/step-accuracy/global`, `/progress/weak-spots`, plus `/progress/summary.text` | JSON: required; `.text`: soft (see Text mode) |
| `puzzles.py` | `GET /puzzles/next`, `POST /puzzles/{id}/attempts`, `GET /puzzles/summary`, `GET /puzzles/themes`, plus `.text` variants of each | JSON: required; `.text`: soft |
| `users.py` (`/users`) | `GET /users/me/preferences`, `PATCH /users/me/preferences` | required |
| `app.py` | `GET /` (HTML stub), `GET /ping`, `GET /dashboard.text` | public / soft |

`GET /progress/step-accuracy/global` requires login but aggregates every user's responses
(it finds broadly confusing steps), so it is not scoped to the caller.

### Services (`backend/app/modules/*/service.py`)
- `training/service.py`
  - `create_training_session`: picks the requested opening (or a random opening the user has not
    trained yet), validates the move sequence against the opening's EPD/start position, and
    creates one `TrainingItem` per ply. `player_color` is normalized to `"w"` or `"b"`.
  - `create_session_from_due`: builds a review session from up to 10 due positions.
    The session has `opening_eco=NULL, opening_name="Review"`; each item carries its own
    `opening_eco`/`opening_name`.
  - `get_current_training_item`: first item with no correct response.
  - `submit_training_response`: enforces session ownership and that the submitted item is the current
    one, validates via `chess_rules`, upserts the `TrainingResponse`, calls
    `progress.record_attempt` inside a savepoint (a failure there is logged and swallowed), and
    marks the session `completed` when every item has a correct response.
  - `create_training_items`: bulk item insert (rejects duplicate `order_index`).
- `progress/service.py`: `record_attempt` (upsert `PositionProgress`, advance SM-2, update streak),
  `record_streak`, `get_summary`, `get_due`, `get_weak_spots` (aggregated per opening),
  `get_step_accuracy` / `get_global_step_accuracy` (per opening ply, trainee-authored plies only,
  top 5 wrong moves).
- `puzzles/service.py`: `get_next_puzzle` (due puzzle first, else unseen by popularity; with
  `theme`, free-practice mode over unsolved puzzles with that tag), `submit_puzzle_attempt`
  (multi-move puzzles: opponent replies are auto-played, and SRS/streak bookkeeping happens only
  when the puzzle is finished or a move is wrong), `get_theme_counts`, `get_puzzle_summary`.
- `openings/service.py`: `get_prompt_and_move()`, currently unreferenced by routers.
- `email/sender.py`: `send_verification_email` (runs as a FastAPI background task), and
  `supported_languages()`, which reads the locale filenames from
  `frontend/packages/i18n-locales/locales/`.

### Domain Models

| Table | Model | Notes |
|---|---|---|
| `users` | `User` | credentials, `is_active`, email-verification fields, and preferences (`language`, `theme`, `board_theme`, `piece_set`, `show_coordinates`, `board_animations`, `board_orientation_mode`, `sound`) |
| `openings` | `Opening` | composite PK (`eco`, `name`); `epd`, `pgn`, `uci_moves`, `description` |
| `training_sessions` | `TrainingSession` | `status` (`active`/`completed`), `user_id`, `opening_eco`/`opening_name`, `player_color` |
| `training_items` | `TrainingItem` | one per ply: `order_index`, `fen`, `correct_move_uci`; optional own `opening_eco`/`opening_name` (review sessions) |
| `training_responses` | `TrainingResponse` | submitted move, `is_correct`, `reason`, `fen_after` |
| `position_progress` | `PositionProgress` | per user + `fen` + `correct_move_uci` (unique): counts and SM-2 state |
| `user_streaks` | `UserStreak` | one row per user: current/longest streak, `last_active_date` |
| `puzzles` | `Puzzle` | Lichess puzzle subset; `moves[0]` is the opponent's setup move |
| `puzzle_progress` | `PuzzleProgress` | per user + puzzle (unique): counts, `hint_used`, SM-2 state |

`TrainingSession.opening_eco`/`opening_name` are plain `String` columns with no ORM
`ForeignKey`/`relationship` to `Opening`, but a composite FK (`fk_training_sessions_openings`,
`ondelete="RESTRICT"`) is enforced at the DB level (migration `7f740a9c4e3a`). So
`session.opening` isn't navigable in Python, and the database won't let an opening be deleted
while a session references it. Review sessions set `opening_eco` to NULL, so the composite
FK does not apply to them.

`training_items.opening_eco`/`opening_name` have no FK.

### Rules / Validation Helpers
- `modules/training/chess_rules.py`: `validate_and_apply()` parses a UCI move, checks legality, and
  compares against the expected move. Training and puzzles share it. Its outputs are a contract
  every frontend depends on (see `AGENTS.md`).
- `modules/progress/srs.py`: SM-2. Correct answers score quality 5, wrong answers 2; a wrong
  answer resets repetitions and schedules the item 1 day out. Intervals are capped at 365 days.
  "Mastered" in the summaries means `repetitions >= 2`.
- `modules/progress/streak.py`: consecutive-day streak counting.

### Text mode
Routes ending in `.text` return plain-text (ANSI-colored unless `?ansi=false`) output for
terminal clients: `/dashboard.text`, `/progress/summary.text`, `/puzzles/next.text`,
`POST /puzzles/{id}/attempts.text`, `/puzzles/summary.text`, `/puzzles/themes.text`. They use
`get_current_user_or_none` and answer an unauthenticated caller with a `401` plain-text login
hint instead of the JSON error body. Rendering helpers live in `modules/shared/`
(`ansi.py`, `text_mode.py`) and `modules/puzzles/text_rendering.py`. nginx redirects a bare `/`
from `curl`/`wget`/`httpie` user agents to `/api/dashboard.text` (`nginx/terminal-client.conf`
and `nginx/conf-prod/terminal-client.conf`, kept identical).

### DB Plumbing / Migrations
- `modules/shared/db.py`: engine (`pool_pre_ping`), `SessionLocal`, `Base`, `get_db`.
- `app/migrations/` (Alembic): `env.py` imports every `modules/*/models.py` to build
  `target_metadata` and loads `.env` from the repo root. Versions run from `0001` through
  `0013` plus a few hash-named early revisions. The `api` compose service runs
  `alembic upgrade head` before starting uvicorn.

### Configuration (environment)
`DATABASE_URL`, `JWT_SECRET` (requests fail with 500 if unset), `JWT_ALGORITHM` (default
`HS256`), `JWT_EXPIRES_MINUTES` (60), `JWT_REFRESH_EXPIRES_DAYS` (7), `EMAIL_VERIFY_EXPIRES_HOURS` (24),
`EMAIL_VERIFICATION_REQUIRED` (default off), `SMTP_*`, `FRONTEND_URL`, `SENTRY_DSN` /
`SENTRY_ENVIRONMENT`. With no `SMTP_HOST`, the verification link is logged instead of sent.

### Data Import Scripts (repo-root `scripts/`)
- `import_openings.py`: downloads the lichess ECO TSVs, computes EPD/UCI move lists with `python-chess`,
  and upserts into `openings` with raw `psycopg`. Run via `docker compose exec api python scripts/import_openings.py`.
- `import_puzzles.py`: streams the Lichess puzzle CSV (`.zst`), keeps a popularity-ranked subset
  spread across rating buckets, and loads `puzzles`.
- `apply_opening_descriptions.py`, `backfill_opening_descriptions.py`, and
  `backend/scripts/apply_all_description_batches.py` populate `openings.description`.

None of these are part of the request path.

## Key Architecture Decisions

| Decision | Implementation |
|---|---|
| API design | FastAPI routers grouped by feature area, all mounted at the root (`prefix=""`); nginx exposes them under `/api/` |
| API casing | `training`, `progress` and `puzzles` responses/requests extend a per-file `CamelModel` (`alias_generator=to_camel`), so JSON is camelCase. `auth`, `openings` and `users` return snake_case keys (`access_token`, `uci_moves`, `board_theme`, ...) |
| Business logic placement | Training, progress and puzzle workflows live in `modules/*/service.py`; auth logic lives in `routers/auth.py`; preferences validation lives in `routers/users.py` |
| Domain boundaries | Feature-specific model files (`modules/*/models.py`) |
| Rules location | Move legality/correctness in `modules/training/chess_rules.py`; SM-2 in `progress/srs.py` |
| Persistence and migrations | Central DB plumbing in `modules/shared/db.py`, Alembic migrations in `app/migrations/` |
| Authorization | Stateless JWTs (`type` claim: `access`, `refresh`, `email_verify`); only `access` tokens are accepted for API calls. Data is scoped to `current_user.id` |
| Email verification | Optional via `EMAIL_VERIFICATION_REQUIRED`. When on, login returns 403 until verified; token version on the user invalidates older links |
| Spaced repetition | Per-position (`PositionProgress`) and per-puzzle (`PuzzleProgress`) SM-2 state; review sessions are seeded from due positions |
| Opening / puzzle data import | Offline scripts using raw `psycopg`, not part of the request path |
| Error reporting | Sentry initialised in `app.py` only when `SENTRY_DSN` is set |

## Frontends & Shared Chess Core

The backend is UI-agnostic. Three frontends call the root-absolute `/api`, so everything is
same-origin (no CORS middleware): `frontend/react/` (Vite, served at `/`), `frontend/angular/`
(served at `/angular/`) and `frontend/rails/` (served at `/rails/`). nginx is the only
integration point.

Chess logic that is **not** UI-specific (FEN handling, move validation, opening-preview
positions, timeline/next-item/status helpers, all `chess.js`, no framework code) lives in a
standalone package, `frontend/packages/chess-core` (`@knight-school/chess-core`):

- **Shared, not copied.** Each frontend depends on it via a **`file:` dependency**
  (`file:../packages/chess-core`), giving one source of truth.
- **Isolated `node_modules`.** No npm workspaces / hoisting: each frontend keeps its own
  dependency tree; only the built package is shared.
- **Built + tested independently.** `tsup` emits an ESM bundle + `.d.ts`; the package's own
  vitest suite exercises the real `chess.js`. Its CI job is `.github/workflows/core.yml`.
- **Consumed via `dist/`.** Editing `src/` requires `npm run build` in the package, or the frontends
  run stale logic.
- **Docker.** The `react`, `angular` and `rails` Dockerfiles each build the package (its own
  isolated install + build) before installing their own dependencies, which resolves the
  `file:` dep against it.

Translations are shared the same way: `frontend/packages/i18n-locales` is read by the
frontends and by the backend (`modules/email/sender.py`, for the verification email and the set
of supported languages).
